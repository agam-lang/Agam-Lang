# Ground-Truth Audit: Does Every `opt` Pass Transform MIR?

**Audit date:** 2026-09-05  
**Method:** Each pass body was read for writes to `block.instructions`, `function.blocks`, `block.terminator`, `instr.op`, or another `MirFunction`/`MirModule` field. Matching or iterating over MIR is not counted as transformation. Status keys: 🟢 transforms MIR; 🟡 has both transformation and analysis-only paths; ⚪ analysis/reporting-only.

## Pipeline registration and wiring

The default fixed-point loop invokes `inline`, `constant_fold`, `egg_engine`, `loop_unroll`, a second `constant_fold`, `dce`, then escape reporting at `agam/crates/middle/agam_mir/src/opt/mod.rs:42-57`:

```rust
changed |= inline::run(module);
changed |= constant_fold::run(module);
changed |= egg_engine::run(module);
changed |= loop_unroll::run(module);
changed |= constant_fold::run(module);
changed |= dce::run(module);

let (_escapes, promo) = escape::run_escape_and_promote(module, &purity);
if promo.total_promoted > 0 {
    changed = true;
}
```

`vectorize` and `polyhedral` are exported from the same module at `opt/mod.rs:13-14`, but neither is called by this loop. Outside their own source/tests, the only polyhedral use is the `AffineExpr` type in `agam/crates/middle/agam_mir/src/scev/lower_to_affine.rs:1-11`; no call to `vectorize::run`, `vectorize_function`, or a polyhedral scheduling function exists outside their own files/tests (repository search, 2026-09-05).

## Verdict

This is **not** systemic across the default transforming passes: `inline`, `constant_fold`, `egg_engine`, `loop_unroll`, and `dce` each make a literal MIR write, and the unwired `vectorize` pass also literally rewrites MIR. The naming/reporting defect is real for **`escape`**, which is analysis/reporting-only despite “promotion” counters and a mutable function parameter, and for **`polyhedral`** only if its module-level “transformations” wording is interpreted as a claim to rewrite MIR; it constructs schedule/domain data only. Test-strength debt is broader but distinct: `vectorize` tests prove success and verifier acceptance rather than a specific post-transform shape, and `loop_unroll`’s positive test observes the whole optimizer pipeline rather than directly isolating its own pass.
